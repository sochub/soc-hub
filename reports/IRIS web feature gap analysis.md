# Build the timeline first, then assets and OIDC

SOC Hub's biggest gap against DFIR-IRIS is not a long tail of features but one structural object: a dated, categorised **investigation timeline** linked to indicators and hosts. IRIS's timeline is the feature that comparison sites single out as its differentiator over TheHive, the single most-upvoted open request in TheHive's own tracker (**13 👍**, open since 2017) is "add a case timeline section", and SOC Hub's current `timeline_events` table carries only `event_type`, `content` and an insertion timestamp, which makes it an activity log rather than a timeline ([TheHive #84](https://github.com/TheHive-Project/TheHive/issues/84); [staquest](https://staquest.com/compare/dfir-iris-vs-thehive); SOC Hub `backend/app/models/case.py`). Behind the timeline, three further gaps combine high community demand with a wholly missing SOC Hub counterpart: a **case assets model** (hosts/accounts linked to events and IOCs; the object SANS ISC praised most in IRIS), a **notes subsystem** (where IRIS's most damaging reliability complaints live, so a correct implementation is a differentiator), and **OIDC login**, IRIS's most-demanded single item at **14 👍 / 21 comments** that SOC Hub only half-covers with SAML ([SANS ISC 29880](https://isc.sans.edu/diary/29880); [iris-web #628](https://github.com/dfir-iris/iris-web/issues/628); [iris-web #370](https://github.com/dfir-iris/iris-web/issues/370)). The picture is not one-sided: SOC Hub already ships things IRIS users are still asking for or that IRIS only reaches in its v3 beta, including per-severity SLA tracking (requested in IRIS on 2026-10-08), @mentions and followers, an AI copilot with confirmable actions, a DAG workflow engine with dry-run, a guest portal, user-level timezones and a separate raw-artifact register distinct from curated IOCs ([iris-web #1151](https://github.com/dfir-iris/iris-web/issues/1151); [iris-web #779](https://github.com/dfir-iris/iris-web/issues/779)). The recommended order is therefore: finish the `case_events` timeline now (with a "set to now" button, timezone capture and correctly escaped CSV, each of which answers a specific IRIS issue), add OIDC and a minimal assets table in the same quarter, then notes, evidence chain of custody, MISP/OpenCTI and tenant-editable report templates next, and leave time tracking, custom attributes, per-case ACLs and multi-timeline visualisation for later. A caution on the evidence: IRIS is a low-reaction community where the most-upvoted issue in its history has 14 👍, so rankings below triangulate reactions, comment counts, duplicate issues and external write-ups rather than relying on any one number.

## IRIS is a case-centred DFIR workspace whose core is case → timeline, IOCs, assets, notes, tasks, evidence

DFIR-IRIS (`dfir-iris/iris-web`) is an LGPL-3.0 incident-response case platform sponsored by Deutsche Telekom Security, with **1,595 stars, 334 forks** and roughly 390–440 open issues on 2026-10-18 (two API pulls on the same day returned 389 and 439) ([GitHub repos API](https://api.github.com/repos/dfir-iris/iris-web); [dfir-iris.org](https://dfir-iris.org/)). It exists in two live lines: **v2.4.29 is the latest stable** (jQuery/Jinja UI on a Flask monolith, Postgres 12, tagged 2026-04-28) and **v3.0.0-beta.x is an active rebuild** (SvelteKit frontend, backend split into `iris-backend`, Postgres 18, `/api/v2` only), with beta tags landing every few days through September–October 2026 and the README still warning that v3 is "not recommended for production use" ([iris-web README](https://github.com/dfir-iris/iris-web/blob/master/README.md); [GitHub tags](https://api.github.com/repos/dfir-iris/iris-web/tags)). Its rise is largely a TheHive story: TheHive 5 moved to a commercial model and TheHive 4 lost support at the end of 2022, and both the SANS ISC review and the CERT.PT migration talk name that as the trigger for adopting IRIS ([SANS ISC 29880](https://isc.sans.edu/diary/29880); [CERT.PT slides](https://csirt.fct.pt/wp-content/uploads/2025/06/04-DFIR-IRIS-Jorge-Loureiro.pdf)).

A case in IRIS is a container for a markdown summary, **timeline events, IOCs, assets, notes in directories, evidences, datastore files, tasks**, comments on every object, custom attributes, an asset/IOC graph and per-case access control; every object carries `custom_attributes` JSON and a `modification_history` JSON audit trail, and v3 adds followers, vulnerabilities, export/import, multiple named timelines and war rooms ([models/cases.py @v2.4.29](https://raw.githubusercontent.com/dfir-iris/iris-web/v2.4.29/source/app/models/cases.py); [iris-backend openapi](https://raw.githubusercontent.com/dfir-iris/iris-backend/develop/source/app/blueprints/rest/openapi.generated.yaml)). Cases are always attached to a **customer** (`client_id NOT NULL`), carry a classification, severity, state, outcome (`false_positive`, `true_positive_with_impact`, …), reviewer and review status, and can be seeded from an admin-managed case template that pre-fills title prefix, summary, tags, tasks and note directories but never IOCs or assets ([docs case templates](https://docs.dfir-iris.org/latest/operations/case_templates/)).

No usage telemetry exists, so "most used" must be inferred from documentation order, API surface and changelog frequency, and all three point the same way. The docs homepage lists Alerts, Cases, IOCs, Tasks, Notes, Evidence, Timeline, War Rooms, Modules ("162 hook bindings"), REST API, Access Control and Reports; the v3 OpenAPI spec has **548 `/api/v2` paths**, of which manage (126), mcp (110), war-rooms (95) and cases (59) dominate; and the Quick Start sizes hardware for "about 20 users, ~200 alerts per day, and a dozen ongoing cases", which says alerts are the primary ingestion path ([docs home](https://docs.dfir-iris.org/latest/); [docs getting started](https://docs.dfir-iris.org/latest/getting_started/)). Release notes since 2023 are overwhelmingly about alerts (similarity, filters, resolution statuses, correlation performance, alerts-only groups), and the v3 migration guide names "war rooms, alert clusters, and investigation flows" as "the most-used additions" ([GitHub Releases](https://github.com/dfir-iris/iris-web/releases); [docs migrate_to_v3](https://docs.dfir-iris.org/latest/operations/upgrades/migrate_to_v3/)). Extensibility runs through Python modules on ~160 pre/post hooks, but only the webhooks module has been touched since 2024 (last push 2025-08-31); the VT and MISP modules are frozen since 2023–2024, so hooks and webhooks, not the module catalogue, are what people actually rely on ([GitHub org repos](https://api.github.com/orgs/dfir-iris/repos)). Finally, the maintainers paused new-feature work in May 2023 to focus on stability and a refactor and publish no long-term roadmap, which is why the oldest high-reaction requests below are still open: demand has accumulated rather than been served ([docs roadmap](https://docs.dfir-iris.org/latest/roadmap/)).

Three patterns matter more than any single row. First, the items that recur across **both** IRIS and TheHive and across 2017–2026 (SSO, image paste, task libraries, ATT&CK, bulk alert operations, auto-run enrichment, metrics export, email, Kubernetes) are durable rather than fashionable demands and are the safest bets ([TheHive issues by reactions](https://github.com/TheHive-Project/TheHive/issues?q=is%3Aissue+sort%3Areactions-%2B1-desc)). Second, many of IRIS's highest-reaction asks are small affordances (a "current time" button, drag-drop images, PDF export of a note, a sortable table), which a competitor can win cheaply on polish. Third, the 2026 comparisons converge on "TheHive for alert triage and IRIS for deep investigations" as the market's unfilled seam; nobody is seen as doing both well for free, which argues for SOC Hub keeping its triage strengths while adding IRIS-grade investigation objects ([pistack](https://www.pistack.xyz/posts/2026-05-17-self-hosted-soc-case-management-thehive-cortex-iris-guide/)). Items the brief asked about that surfaced **no** measurable demand in either tracker are kanban boards, keyboard shortcuts (a single IRIS bug), dark mode (v3 has a toggle), STIX import and Plaso/super-timeline import (one 2022 Timesketch mention), so they should not drive priorities.

## The investigation timeline: match IRIS's `cases_events` semantics in v1, grow toward named timelines in v2

SOC Hub's existing "timeline" tab is an **activity log**: `timeline_events` rows are typed comments (`comment`, `status_change`, `artifact_added`, guest entries) stamped with `created_at`, with no occurrence date, title, category, links or flags, and the four milestone dates live separately on `case_reports` (SOC Hub `backend/app/models/case.py`, `backend/app/models/case_report.py`). IRIS's timeline is a different object entirely: an analyst-curated record of **what happened on the victim estate and when**, independent of when the analyst wrote it down. The planned first version, a `case_events` table with `event_date, title, content, raw, source, category (IRIS/ATT&CK tactic list), tags, flagged, in_summary` and linked artifacts, exposed as a filterable day-grouped list with CSV export and `in_summary` events feeding the PDF report, is the right scope and maps almost one-to-one onto IRIS's schema. Keep the existing activity tab (rename it "Activity") rather than merging the two; IRIS's own experience shows the activities feed and the timeline are distinct reports (Investigation vs Activities) ([docs reports](https://docs.dfir-iris.org/latest/operations/reports/)).

### Data model: what IRIS stores and what v1 should take from it

IRIS's `cases_events` table is byte-identical between v2.4.29 and v3 and carries: `event_date` (stored UTC-normalised and used as the canonical sort/filter key), `event_tz` (an offset string such as `"+00:00"`) and `event_date_wtz` (the wall-clock time the analyst typed, kept purely for redisplay); `event_title`, `event_content` (markdown), `event_raw`, `event_source`; `event_tags` as comma-separated text; `event_color` from a fixed seven-value palette; three booleans `event_in_summary` (include in the curated/visual timeline), `event_in_graph` (include this event's asset/IOC links in the case graph) and `event_is_flagged` (triage marker and filter); a self-referential `parent_event_id` with a check constraint; `event_added` and `user_id` for provenance; JSONB `modification_history` and `custom_attributes`; one category per event via a junction with a unique `event_id`; and M2M junctions to assets and IOCs plus a comments link table ([models/cases.py @v2.4.29](https://github.com/dfir-iris/iris-web/blob/v2.4.29/source/app/models/cases.py); [iris-backend models/cases.py](https://github.com/dfir-iris/iris-backend/blob/develop/source/app/models/cases.py)). The seeded category list is **Unspecified, Legitimate, Remediation** plus twelve ATT&CK tactics (Initial Access through Impact), and the official Python client describes the field as "Category of the event (MITRE ATT@CK)" ([post_init.py @v2.4.29](https://github.com/dfir-iris/iris-web/blob/v2.4.29/source/app/post_init.py); [iris-client case.py](https://github.com/dfir-iris/iris-client/blob/master/dfir_iris_client/case.py)). Two things to note when copying that list: it predates the two pre-compromise tactics (Reconnaissance, Resource Development) in current ATT&CK Enterprise, which SOC Hub can include from the start, and IRIS users asked for admin-defined custom categories ([#301](https://github.com/dfir-iris/iris-web/issues/301), 1 👍), which a fixed enum in v1 can defer without blocking.

The recommended v1 table, in SOC Hub's conventions, is therefore `case_events(id, tenant_id, case_id, event_date timestamptz NOT NULL, event_tz varchar(6) NOT NULL default '+00:00', title text NOT NULL, content text, raw text, source text, category enum NOT NULL default 'unspecified', tags JSON, flagged bool default false, in_summary bool default false, in_graph bool default true, parent_event_id FK case_events NULL, created_by FK users, created_at, updated_at)` with `case_event_artifacts(event_id, artifact_id)` and an index on `(case_id, event_date)`. Three additions to the planned column list cost nothing now and are expensive to retrofit: **`event_tz`** (IRIS users cannot get the UTC offset back out in reports, [#997](https://github.com/dfir-iris/iris-web/issues/997), and timezone confusion is a recurring complaint, [#730](https://github.com/dfir-iris/iris-web/issues/730) 3 👍), **`in_graph`** defaulting to true so the per-case `network` tab can later be fed from events exactly as IRIS does ([case_events_db.py](https://github.com/dfir-iris/iris-web/blob/v2.4.29/source/app/datamgmt/case/case_events_db.py)), and a nullable **`parent_event_id`** so child events and the tree view can arrive in v2 without a migration on a populated table. Store `event_date` as timezone-aware UTC and derive the "as typed" display from `event_date` plus `event_tz` instead of persisting a second datetime; that keeps IRIS's semantics with one fewer column. Skip `custom_attributes`, `modification_history` (SOC Hub's platform audit log already records changes) and a colour column in v1; v3 of IRIS itself moved to **deterministic colours keyed off the category** and uses the explicit colour only as an override ([timeline-event-card.svelte](https://github.com/dfir-iris/iris-frontend/blob/master/src/routes/(app)/case/%5Bcase_id%5D/timeline/components/timeline-event-card.svelte)). Linking to **artifacts** (SOC Hub's raw register) rather than IOCs is the correct choice for v1 because artifacts are the case-scoped object; once `case_assets` exists, add `case_event_assets` and IRIS's optional "sync IOCs to assets" behaviour.

### API: one list endpoint with AND-filters and pagination, plus CRUD

IRIS's v1 (`/case/timeline/advanced-filter?q=<json>`) and v2 (`GET /api/v2/cases/{id}/events?asset&ioc&tag&title&source&description&raw&category&start_date&end_date&flag&page&per_page`) contracts are semantically identical: substring `ILIKE` filters AND-ed across title/description/source/tag/raw, exact category match, inclusive date range, a flag boolean, "linked to all listed assets", "linked to any listed IOC", explicit id lists, and server-side pagination capped at 500 per page that preserves parent/child lineage across pages ([iris-backend events.py](https://github.com/dfir-iris/iris-backend/blob/develop/source/app/blueprints/rest/v2/case_routes/events.py); [business/events.py](https://github.com/dfir-iris/iris-backend/blob/develop/source/app/business/events.py)). SOC Hub should mirror the v2 shape: `GET /cases/{id}/events` with those query parameters returning `{items, total, page, per_page}`, `POST`, `PUT /cases/{id}/events/{eid}` (flagging is a boolean on the event, as in IRIS v3 where the SPA flags via a full PUT; do not add a separate flag resource), `DELETE`, and a server-side `GET /cases/{id}/events/export.csv` honouring the same filters. Do **not** embed events in `GET /cases/{id}` as the activity log is today; a case with thousands of events (IRIS advertised loading "thousands of events in a sec" back in v1.3.0) needs its own paginated endpoint ([changelog](https://docs.dfir-iris.org/changelog/)). An optional `POST /cases/{id}/events/parse-date` wrapping `dateutil.parser` reproduces IRIS's much-used "magic wand" that accepts epoch seconds, epoch milliseconds and a dozen `strptime` layouts ([iris_engine/utils/common.py](https://github.com/dfir-iris/iris-web/blob/v2.4.29/source/app/iris_engine/utils/common.py)). Emit `case.updated` with `changes={"events": …}` after commit so workflows can react, and write `create_audit_log(entity_type="case_event", …)` rows per mutation.

For CSV, generate it server-side with Python's `csv` module rather than string concatenation; IRIS's client-side export breaks on commas in descriptions and its export columns differ from its import columns, both of which are open complaints ([#976](https://github.com/dfir-iris/iris-web/issues/976); [#639](https://github.com/dfir-iris/iris-web/issues/639)). Use one header for both directions from day one, modelled on IRIS's so analysts migrating from IRIS can round-trip: `event_date_utc, event_tz, event_title, event_category, event_content, event_raw, event_source, event_tags, linked_artifacts, flagged, in_summary, created_by, created_at` (IRIS v2 header: `event_date(UTC),event_title,event_description,event_tz,event_date_wtz,event_category,event_tags,linked_assets,linked_iocs` plus optional `created_by,creation_date`) ([case.timeline.js](https://github.com/dfir-iris/iris-web/blob/v2.4.29/source/app/static/assets/js/iris/case.timeline.js)). CSV import can wait for v2 but the header choice must not.

### UI: a day-grouped list with structured filters, a "set to now" button and curated summary

Both IRIS generations render the timeline as a vertical list ordered by `event_date` ascending, split by **day headers**, with each card showing the time, title, a category pill, the source, a flag icon, asset/IOC chips, `#tag` pills, a comment count and per-card actions (edit, add child, flag, duplicate, share link); v3 adds a quick in-page search with `n/m` match navigation, a collapsible **structured filter form** (Title, Description, Source, Tag, Asset, IOC "contains…", From/Until, Category select, Flagged select) that replaced v2's `key:value AND key:value` mini-language, infinite-scroll pagination, a sticky floating action pill (select mode, add event, fold children, refresh, scroll top/bottom) and multi-select for bulk delete / toggle summary / toggle graph ([timeline-view.svelte](https://github.com/dfir-iris/iris-frontend/blob/master/src/routes/(app)/case/%5Bcase_id%5D/timeline/components/timeline-view.svelte); [timeline-filters.svelte](https://github.com/dfir-iris/iris-frontend/blob/master/src/routes/(app)/case/%5Bcase_id%5D/timeline/components/timeline-filters.svelte); [case_timeline.html @v2.4.29](https://github.com/dfir-iris/iris-web/blob/v2.4.29/source/app/blueprints/case/templates/case_timeline.html)). SOC Hub's v1 should adopt the v3 pattern: a new `events` tab in `CASE_TABS`, a `CaseEvents.tsx` feature component using `useQuery(['case-events', caseId, filters])`, day grouping computed in the **viewer's timezone** via the existing `useMyTimezone` (IRIS groups by the browser's locale date of a UTC value and has an open "date badge off by one" bug, [#722](https://github.com/dfir-iris/iris-web/issues/722)), category pills tinted from a deterministic ten-colour palette keyed by category using the `--color-severity-*`/`--color-accent` tokens, and a filter row built from the existing `Input`/`Button`/`Badge` primitives plus native `<select>` and `<input type="datetime-local">` until the design system gains Select/DatePicker components (the inventory confirms none exist in `frontend/src/components/ui/`).

Three affordances answer specific IRIS requests and should be in v1. A **"Set to now"** button on the event form (IRIS [#294](https://github.com/dfir-iris/iris-web/issues/294), 4 👍, finally present in v3's form as "Set to now (local time and timezone)") that fills `event_date` and `event_tz` from the browser ([timeline-event-form.svelte](https://github.com/dfir-iris/iris-frontend/blob/master/src/routes/(app)/case/%5Bcase_id%5D/timeline/components/timeline-event-form.svelte)). A **"quick-add artifact" field** inside the event form that creates and links an artifact in one step ([#383](https://github.com/dfir-iris/iris-web/issues/383), 2 👍), which SOC Hub can wire to the existing `POST /artifacts/` with `case_id`. And an **"Add to summary" toggle** with bulk select, since in IRIS `event_in_summary` is the curation mechanism that decides what the executive timeline and the visualisation show ("No events in summary" is the empty state of IRIS's visual timeline) ([case_timeline_routes.py](https://github.com/dfir-iris/iris-web/blob/v2.4.29/source/app/blueprints/case/case_timeline_routes.py)). Deep links of the form `/cases/{id}#event-{eid}` already exist for activity entries and notifications; reuse the same scroll-and-highlight for events. Two proactive hooks fit SOC Hub's existing AI layer without new infrastructure: the copilot's `add_timeline_note` action should gain an `add_event` sibling with an `event_date` parameter, and the proactive-suggestion engine that already detects declarative findings can propose dated events when a message contains a timestamp.

### Report: feed `in_summary` events into the PDF and derive milestone defaults

IRIS passes templates a `timeline` list ordered by `event_date` with `event_title, event_content, event_raw, event_date, event_source, category, event_tags, assets, custom_attributes`, and it is the reporter, not the template, that pre-joins asset names ([docs reports](https://docs.dfir-iris.org/latest/operations/reports/); [reporter.py @v2.4.29](https://github.com/dfir-iris/iris-web/blob/v2.4.29/source/app/iris_engine/reporter/reporter.py)). In SOC Hub, `reports/builder.py` should add an `events` list of `in_summary=true` rows (ordered by `event_date`, with artifact values defanged by the existing helper, and `raw` omitted from the "key" mode but included in `full=true`) and `report.html.j2` a "Timeline of events" section rendered as a date-grouped table with category and source columns. Because `case_reports.first_seen_at/detected_at/contained_at/recovered_at` currently have to be typed by hand, the report editor can offer "use earliest event" defaults computed from `case_events` (earliest event overall for first seen, earliest `remediation`-category event for contained) while keeping the columns editable. The Activities report IRIS offers maps onto SOC Hub's existing activity log and platform audit export, so no second report type is needed yet.

### V2 and beyond: assets, child events, named timelines and swim-lanes

Once `case_assets` lands, add `case_event_assets` and IRIS's `sync_iocs_assets` option, and populate the placeholder `network` tab from `in_graph` events exactly as IRIS builds its per-case graph from event→asset and event→IOC edges ([case_events_db.py](https://github.com/dfir-iris/iris-web/blob/v2.4.29/source/app/datamgmt/case/case_events_db.py)). Child events and the tree view (IRIS v2.4.6) follow from the nullable `parent_event_id`; IRIS warns inline when a child's date precedes its parent's and users want drag-to-reparent ([#992](https://github.com/dfir-iris/iris-web/issues/992)). IRIS v3's **named multi-timelines** (`case_timelines` + `case_event_timelines`, each case born with a default "Main", events on zero timelines shown only under "All") solve the real problem of separating "attacker activity" from "network" or "responder" views without duplicating events, and the migration pattern (add table, backfill one default per case, attach existing events) is directly reusable ([iris-backend models/cases.py](https://github.com/dfir-iris/iris-backend/blob/develop/source/app/models/cases.py)). The visual swim-lane view (vis.js in IRIS v2, grouped by asset or category and limited to `in_summary` events; users asked to group by IOC and tag too, [#993](https://github.com/dfir-iris/iris-web/issues/993)) is the lowest-priority piece: v3 of IRIS has not re-shipped it for cases at beta.13, and SOC Hub has no timeline or date library installed, so it should wait until the list view proves the data model. Real-time collaboration (IRIS uses socket.io to patch cards in place) can be approximated with React Query `refetchInterval` on the events query, which is enough for a team of analysts and avoids adding a websocket layer.

## Conclusion

The research reframes the question from "which IRIS features is SOC Hub missing" to "which half of the case does each product own". IRIS owns the inside of the case (dated timeline, assets, notes, evidence custody, closure semantics) and is weak on everything around it; SOC Hub owns the surroundings (ingest, SLA, automation, notifications, AI, guests, tenancy) and has an empty core. Because the missing core objects are additive tables and tabs rather than rewrites, SOC Hub can close the gap faster than IRIS can close its own, and IRIS's v3 transition, which breaks every v1 integration and the official Python client, is exactly the window in which installed bases re-evaluate tooling.

Two consequences follow for execution. Build the timeline to IRIS's schema semantics (UTC `event_date` plus offset, one category per event, `in_summary` as the curation flag, `in_graph` and `parent_event_id` reserved) so later assets, graph and multi-timeline work are migrations of data, not of meaning. And treat IRIS's open bug list as a free specification of where not to cut corners: optimistic locking on notes, server-side CSV with symmetric headers, timezone preserved end to end, and a "set to now" button are each a single issue in IRIS's tracker that has stayed open for years and would each be a visible reason to choose SOC Hub instead.
