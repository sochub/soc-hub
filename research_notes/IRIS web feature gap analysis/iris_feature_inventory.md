# DFIR-IRIS (iris-web) feature inventory, 2025–2026

Research date: 2026-10-18. Scope: dfir-iris/iris-web and sibling repos, docs.dfir-iris.org, dfir-iris.org. Sources were fetched live; where two sources disagree (e.g. release dates), both are cited.

## Release state as of October 2026 (which line is "current"?)

### Takeaway
There are two live lines: **v2.4.29 is the latest stable** (jQuery/Jinja UI, Flask monolith, Postgres 12), and **v3.0.0-beta.x is the actively developed rebuild** (SvelteKit frontend, backend split into `iris-backend`, Postgres 18, `/api/v2` only). The planned v2.5 never shipped as stable; its work was folded into v3. The docs site now documents v3 as "latest".

## Case objects and data model (what a case contains)

### Takeaway
A case in IRIS is a container for: summary (markdown description), timeline events, IOCs, assets, notes in directories, evidences, datastore files, tasks, comments on every object, custom attributes, graph, and access control. All objects carry `custom_attributes` (JSON) and `modification_history` (JSON). v3 adds multiple named timelines per case, asset flags, case vulnerabilities, followers, export/import, and chat/AI surfaces.

### Inferences
- The object set is stable across v2.4 → v3 (the v3 page explicitly lists cases, alerts, IOCs, assets, evidence, timelines, tasks, notes, graph, dashboards, reports, modules/hooks, RBAC as unchanged); the v3 delta is in collaboration (war rooms), alert automation, and AI/MCP surfaces.
- Every object having `custom_attributes` + `modification_history` + comments + module hooks is the core extensibility pattern a competitor must match.

### Gaps
- No documentation found for the IOC types list, event categories list, task statuses list, or analysis/compromise statuses (they are DB-seeded taxonomies; the API exposes `/manage/task-statuses`, `/manage/ioc-types` etc. but I did not enumerate values).

## Which features are most used / most central?

### Takeaway
By every proxy (docs nav ordering, product homepage, API surface counts, hooks, release-note frequency), the core is **Case → (Timeline, IOCs, Assets, Notes, Tasks, Evidence/Datastore)** plus **Alerts triage → case**. Since 2023 the roadmap attention has shifted heavily to **Alerts** (v2.1–v2.4: similarity, filters, resolution statuses, correlation performance) and, in v3, to **War Rooms** and **alert clusters**; **Dashboards** got the only feature additions in the 2.4 line during 2025–2026.

- Hardware sizing in Quick Start assumes "about 20 users, ~200 alerts per day, and a dozen ongoing cases" — [docs getting started](https://docs.dfir-iris.org/latest/getting_started/).

### Inferences
- Alerts are the primary ingestion path (sizing is in alerts/day; most 2.x changelog lines touch alerts), so alerts→case promotion is the workflow to benchmark against.
- Webhooks is the only module still maintained (2025 push); VT/MISP modules are effectively frozen since 2023–2024, suggesting enrichment via modules is less central than the hook/webhook mechanism itself.
- The Python client has not been updated since 2024-08 and docs say it "will be updated to a v3-compatible release" → API automation is used, but the official client lags.

### Gaps
- No telemetry or usage statistics exist; "most used" is inferred from documentation emphasis, API surface and changelog frequency.

## Alerts → case workflow

### Takeaway
Alerts (since v2.1.0, 2023-05) are REST-ingested per customer with severity/status/resolution, IOCs, assets, raw `alert_source_content` and `alert_context` JSON; analysts assign, comment, relate (same IOC/asset), and **escalate to a new case** (with template, selected IOCs/assets, note, tags, optional timeline event) or **merge into an existing case**, with unmerge. v3 adds **alert clusters** (rule-driven grouping with its own status/owner/escalate/merge), **cluster rules**, **investigation flows** (ordered, required steps with per-analyst progress), Lucene search, saved filters and batch escalate/merge.

## Case templates

### Takeaway
Case templates (v2.1.0+) are admin-managed JSON that pre-fill a case at creation: title prefix, classification, summary, tags, tasks, and note directories (formerly note groups) with notes. They do not pre-create IOCs or assets. A public marketplace of templates exists in `iris-resources`.

### Cited Findings
- Fields documented: `name, display_name, description, author, classification (lowercase name matching an existing classification), title_prefix, summary, tags[], tasks[] ({title (required), description, tags}), note_groups[] ({title, notes[] ({title, content})})`; applied via the "Case template" dropdown at case creation; managed under Advanced > Case templates (admin only); more templates in the IRIS Resources GitHub repo — [docs case templates](https://docs.dfir-iris.org/latest/operations/case_templates/).
- DB (`case_template`): `id, created_by_user_id, created_at, updated_at, name, display_name, description, author, title_prefix, summary, tags, tasks, note_directories, classification` — [models.py @v2.4.29](https://raw.githubusercontent.com/dfir-iris/iris-web/v2.4.29/source/app/models/models.py). API v2 `POST /api/v2/manage/case-templates` body: `name, display_name, description, author, title_prefix, summary, tags, classification, note_directories, tasks` (required `name, created_by_user_id`) — [openapi](https://raw.githubusercontent.com/dfir-iris/iris-backend/develop/source/app/blueprints/rest/openapi.generated.yaml).
- Permission bits `case_templates_read 0x100`, `case_templates_write 0x200` — [authorization.py](https://raw.githubusercontent.com/dfir-iris/iris-web/v2.4.29/source/app/models/authorization.py).
- Templates are referenced by the alert escalation dialog ("select a case template") and by v3 mail ingest rules (`case_template_id`) — [docs alerts](https://docs.dfir-iris.org/latest/operations/alerts/); [models/mail.py](https://raw.githubusercontent.com/dfir-iris/iris-backend/develop/source/app/models/mail.py).
- `iris-resources` repo root contains a "Case templates" folder (5 stars, last push 2024-04-14) — [GitHub iris-resources](https://github.com/dfir-iris/iris-resources).

### Inferences
- IRIS templates are "scaffolds", not playbooks: no phases, no per-task ordering/dependencies, no IOC/asset seeds, no automation. A phase-grouped playbook model is a differentiator.

## Reporting (DOCX/HTML/MD templates)

### Takeaway
Reports are admin-uploaded DOCX/Markdown/HTML templates rendered with Jinja-style tags (`{{ }}`, `{% %}`, `{%tr for %}` table loops, `|markdown`, `|count`) over a context of case, evidences, iocs, notes, tasks, timeline (+ assets/custom attributes). Two report types: **Investigation** and **Activities**. Layout changed in v2.3.4 and again in v2.4.6 (templates had to be upgraded). v3 keeps reports; rendering moves to `POST /api/v2/manage/report-templates/{id}/render`, and sitreps in war rooms export to HTML/MD/PDF.

### Cited Findings
- Templates managed under Advanced > Templates (admin only); types Investigation (customer/stakeholder document) and Activities (follow-up of activities on the case); formats DOCX, Markdown, HTML; no tag is mandatory; mistyped tags raise generation errors; variables: `case{name, description, open_date, close_date, opened_by, for_customer, soc_id}`, `evidences{filename, date_added, file_hash, added_by, custom_attributes}`, `iocs{ioc_value, ioc_description, ioc_type, ioc_tags, custom_attributes}`, `notes{note_title, note_content, note_creationdate, note_lastupdate, custom_attributes}`, `tasks{task_title, task_description, task_open_date, task_last_update, task_close_date, task_status, task_tags, custom_attributes}`, `timeline{event_title, event_content, event_raw, event_date, event_source, category, event_tags, last_edited_by, assets, custom_attributes}`; syntax `{% for %}`/`{% endfor %}`, `{%tr for %}` for table rows, `{% if assets|count %}`, `|markdown` filter — [docs reports](https://docs.dfir-iris.org/latest/operations/reports/).
- DB: `report_type`, `case_template_report`, `iris_reports`, `languages` tables — [models.py @v2.4.29](https://raw.githubusercontent.com/dfir-iris/iris-web/v2.4.29/source/app/models/models.py). A sibling repo `docx-generator` exists (last push 2025-06-13) — [GitHub org repos](https://api.github.com/orgs/dfir-iris/repos).

## Access control, users, groups, organisations, API keys

### Takeaway
RBAC = group permission bitmask + per-case access level (`deny_all`/`read_only`/`full_access`) set per group, per user, or per organisation, materialised into `user_case_effective_access`. Customers can also be scoped per user (`user_client` with `allow_alerts`). Service accounts hold API keys; v3 adds named, scoped API keys, server-side sessions, enforced MFA on tokens and OIDC JWT exchange.

### Cited Findings
- Permissions enum (v2.4.29): `standard_user 0x1, server_administrator 0x2, alerts_read 0x4, alerts_write 0x8, alerts_delete 0x10, search_across_cases 0x20, customers_read 0x40, customers_write 0x80, case_templates_read 0x100, case_templates_write 0x200, activities_read 0x400, all_activities_read 0x800, statistics_read 0x1000, custom_dashboards_read 0x2000, custom_dashboards_write 0x4000, custom_dashboards_share 0x8000`; `CaseAccessLevel: deny_all 0x1, read_only 0x2, full_access 0x4`; tables `organisations` (org_name, description, url, logo, email, nationality, sector, type), `organisation_case_access`, `groups` (group_permissions, group_auto_follow, group_auto_follow_access_level), `group_case_access`, `user_case_access`, `user_case_effective_access`, `user_organisation (is_primary_org)`, `user_group`, `user_client (access_level, allow_alerts)`; `User` has `api_key`, `external_id`, `active`, `ctx_case`, UI prefs — [authorization.py @v2.4.29](https://raw.githubusercontent.com/dfir-iris/iris-web/v2.4.29/source/app/models/authorization.py).
- Docs: default groups `Administrator` (server_administrator) and `Analysts` (standard_user), both full case access by default; "Set case access" per group on selected cases; recomputation of effective access "can take time on large instances" — [docs groups](https://docs.dfir-iris.org/latest/operations/access_control/groups/). Users: fields Full Name, Login, Email, Password, "Is service account" (API-only, no UI login, no password); permissions only via groups; deactivated users lose login and API key; deletion only if the user never acted on the platform — [docs users](https://docs.dfir-iris.org/latest/operations/access_control/users/).
- API auth: every user gets an API key at creation (My Settings), sent as `Authorization: Bearer`; Renew revokes the previous key — [docs API](https://docs.dfir-iris.org/latest/operations/api/).
- Auth providers: LDAP with local fallback (v2.2.3), OIDC beta (v2.4.13), MFA (`enforce_mfa` server setting; hybrid OIDC/local + MFA fix v2.4.16) — [GitHub release v2.2.3](https://github.com/dfir-iris/iris-web/releases/tag/v2.2.3); [docs changelog](https://docs.dfir-iris.org/latest/changelog/); [models.py ServerSettings](https://raw.githubusercontent.com/dfir-iris/iris-web/v2.4.29/source/app/models/models.py).
- v3: "Named API keys with scope masks, self-service under `/api/v2/me/api-keys`"; "MFA is enforced on token-authenticated endpoints, with a brute-force throttle"; "OIDC adds a session-to-JWT exchange endpoint"; sessions "now tracked server-side so they can be revoked"; all sessions closed on upgrade, API keys unaffected — [docs changelog](https://docs.dfir-iris.org/latest/changelog/); [docs/upgrade-to-3.0.0.md](https://github.com/dfir-iris/iris-web/blob/master/docs/upgrade-to-3.0.0.md).
- v2.4.6 "Access control feature associating users with customers" (important ACL changes) — [docs changelog](https://docs.dfir-iris.org/latest/changelog/).

### Inferences
- IRIS has no true multi-tenancy: one instance = one organisation of analysts; "customers" are the client dimension, and isolation is per-case/per-customer ACL rather than tenant rows.

### Gaps
- Organisation feature is in the schema but not documented in the user/group docs pages; its practical use is unclear.

## Modules, hooks, webhooks, MISP/VT integrations

### Takeaway
Extensibility = Python "modules" (pipeline or processor) installed into the app and worker containers, registering to ~160 hooks (`on_preload_*`, `on_postload_*`, `on_manual_trigger_*`) that run as RabbitMQ/Celery tasks ("DIM tasks"). Official natives: VT, MISP, Webhooks, Check, EVTX, Seika.io, IntelOwl. The Webhooks module is the only one actively maintained; v3 keeps hooks and adds a built-in webhooks model, MCP server and AI workflows.

### Cited Findings
- Module types: pipeline (evidence upload/processing, e.g. EVTX → Splunk) and processor (act on hooks, e.g. enrich IOC via VT/MISP); must be installed in both iris-webapp and worker; managed under Advanced > Modules (admin); official list: IrisVTModule, IrisMispModule, IrisWebHooksModule (manual install), IrisCheckModule (logs every hook), IrisEVTXModule (pipeline) — [docs modules](https://docs.dfir-iris.org/latest/operations/modules/).
- DB: `iris_module` (`module_human_name, module_name, module_description, module_version, interface_version, is_active, has_pipeline, pipeline_args, module_config, module_type`), `iris_hooks`, `iris_module_hooks` — [models.py](https://raw.githubusercontent.com/dfir-iris/iris-web/v2.4.29/source/app/models/models.py).
- Hooks reference: preload (sync, pre-commit), postload (post-commit, list of SQLAlchemy objects), manual (user menu). Hooks exist for case (create/delete/update + manual), alert (create/update/delete/escalate/merge/unmerge + comment hooks), asset, note, ioc, event (incl. `on_preload_event_duplicate`), evidence, task, global task (each create/update/delete pre+post, manual, comment hooks), report (investigation + activities), incident (create/update/delete/alert_add/alert_remove/escalate), and war room (room/member/case/note/task/chat/timeline/sitrep/datastore events). Registration via `IrisModuleInterface.register_to_hook(module_id, iris_hook_name, manual_hook_name=None, run_asynchronously=True)` — [docs hooks](https://docs.dfir-iris.org/latest/development/hooks/).
- Webhooks module: JSON config with `instance_url` and `webhooks[]` (`name, active, trigger_on, request_url, use_rendering, request_rendering ∈ {none, markdown, markdown_slack, html}, request_body`); triggers = specific hooks or `all`, `all_create`, `all_update`; rendered mode placeholders `%TITLE%`/`%DESCRIPTION%`; raw mode `${{ object.field }}`; status visible in DIM Tasks; known gaps: IOC events carry no case info, asset update events no user info; targets Discord/Slack/Teams/Tines/Shuffle — [docs IrisWebHooks](https://docs.dfir-iris.org/latest/operations/modules/natives/IrisWebHooks/). v2.4.23 bundles webhooks module v1.0.9 — [GitHub release v2.4.23](https://github.com/dfir-iris/iris-web/releases/tag/v2.4.23).
- MISP module: IOC types ip-*, domain, md5/sha224/sha256/sha512; manual "Get MISP insight" or auto on IOC create/update (both off by default); single MISP instance; writes insight as IOC attribute via Jinja2 templates; "in its early stage" — [docs IrisMISP](https://docs.dfir-iris.org/latest/operations/modules/natives/IrisMISP/).
- Custom attributes: "The VT module adds a `VT report` attribute" — [docs custom attributes](https://docs.dfir-iris.org/latest/operations/custom_attributes/).
- Module repos: iris-vt-module (4 stars, last push 2023-10-05), iris-misp-module (7, 2024-05-15), iris-evtx-module (7, 2024-05-21), iris-webhooks-module (0, 2025-08-31), iris-intelowl-module (3, 2024-02-09), iris-seika-module (0, 2024-08-29), iris-check-module (0, 2023-02-02), iris-module-interface (2, 2023-03-25), iris-skeleton-module (2, 2022-06), iris-mwdb-module (0, 2022-06) — [GitHub org repos API](https://api.github.com/orgs/dfir-iris/repos).
- v3 backend has `webhooks.py` model and `POST /api/v2/manage/webhooks/legacy-module/import`, module config export/import, `/manage/modules/hooks`, and `/cases/{id}/dim-hooks/invoke` / `/alerts/dim-hooks/invoke`; legacy `POST /dim/hooks/call` has "no v2 replacement" — [openapi](https://raw.githubusercontent.com/dfir-iris/iris-backend/develop/source/app/blueprints/rest/openapi.generated.yaml); [legacy map](https://docs.dfir-iris.org/latest/api_reference/legacy_endpoints/).
- Legacy GraphQL API (added v2.4.8) was removed in v2.4.28 (GHSA-3mxh-x92q-9r25) — [docs changelog](https://docs.dfir-iris.org/latest/changelog/).

### Inferences
- Module development has stagnated; v3's built-in webhooks model and MCP/AI workflows look like the replacement path for integrations rather than new Python modules.

### Gaps
- `iris-module-interface` current version and whether v3 changes the module interface are undocumented.

## Dashboards, search, war rooms, and other v3 subsystems

Custom dashboards (widgets with JSON definitions, shareable) arrived late in the 2.4 line (v2.4.25–26, late 2025) and are the only new feature there. v3 adds war rooms (chat/threads/polls/decisions/sitreps/teams/scope IOC+asset staging), notifications with @mentions, cross-element search, case export/import, case chat/AI assistant, AI workflows, MCP server (≈50 tools), mail ingestion, keystore/secrets, banners and avatars.

## API v2, Python client, and the v2 → v3 migration

### Takeaway
IRIS has had `/api/v2` since v2.5-beta; v3 makes it the **only** reachable API (legacy `/case/*`, `/manage/*`, `/alerts/*`, `/datastore/*`, `/dim/*`, `/global/*` are 404 behind the SvelteKit proxy). A published migration map covers each object. The official Python client is stale (2024-08) and will be re-released for v3.

### Cited Findings
- v2.4.x API versions: v2.0.x→API 2.0.0, v2.1–2.2→2.0.1, v2.3→2.0.2, v2.4→2.0.4, develop→2.1.0; cases example `GET /manage/cases/list?cid=1` — [docs API](https://docs.dfir-iris.org/latest/operations/api/).
- v2.5.0-beta.1: "New `/api/v2` REST API for cases, case assets, IOCs, tasks, alerts, context, and dashboard, with consistent pagination and HTTP status codes"; deprecation notices on legacy endpoints; first SvelteKit interface in `ui/`; Python 3.12 — [docs changelog](https://docs.dfir-iris.org/latest/changelog/).
- v3: "nginx hands every request to the `frontend` service, whose SSR proxy only forwards three prefixes to `app` — `/api/v2/*`, `/auth/*` and `/static/*`. A v1 path now returns the frontend's 404 page"; capabilities without v2 counterpart: bulk CSV import endpoints, `POST /case/tasklog/add` (activities feed is read-only via `GET /api/v2/cases/{id}/activities`) — [docs/upgrade-to-3.0.0.md](https://github.com/dfir-iris/iris-web/blob/master/docs/upgrade-to-3.0.0.md).
- Migration map highlights: `POST /manage/cases/add → POST /api/v2/cases`; `POST /case/ioc/add → POST /api/v2/cases/{case}/iocs`; events → `/api/v2/cases/{case}/events`, list via `/timelines`; evidences → `/api/v2/cases/{case}/evidences`; datastore → `/api/v2/cases/{case}/datastore/{tree,files,folders}`; alerts single/batch escalate+merge; comments per object type; users/groups/customers under `/api/v2/manage/*`; report generation → `/api/v2/manage/report-templates/{id}/render`; unmapped: `/case/export`, `/case/timeline/state`, `/dim/hooks/call`, `/filters/*`, several manage list helpers; "Broken in v3.0.0-beta.1: deleting a note directory (route registered with a missing slash)" — [legacy endpoint migration map](https://docs.dfir-iris.org/latest/api_reference/legacy_endpoints/).
- DB upgrade: PG12 → PG18 via `scripts/upgrade-db-pg12-to-pg18.sh` (logical dump/restore, needs ~3× `db_data` free, 1–5 min/GB), md5 → scram-sha-256; Helm/EKS manifests "v2-era, not usable for v3.0.0-beta.1" — [docs/upgrade-to-3.0.0.md](https://github.com/dfir-iris/iris-web/blob/master/docs/upgrade-to-3.0.0.md); [docs migrate_to_v3](https://docs.dfir-iris.org/latest/operations/upgrades/migrate_to_v3/).
- Python client `dfir_iris_client`: PyPI, LGPL-3.0, 31 stars, 196 commits, version tracks API version (e.g. API v2.0.1 ↔ client 2.0.1); docs at client.docs.dfir-iris.org list modules Session, Case, Administration, Customers, Global search, Users, Helpers; last push 2024-08-19; migration guide says it "will be updated to a v3-compatible release" — [GitHub iris-client](https://github.com/dfir-iris/iris-client); [client docs](https://client.docs.dfir-iris.org/); [GitHub repos API](https://api.github.com/repos/dfir-iris/iris-client); [docs migrate_to_v3](https://docs.dfir-iris.org/latest/operations/upgrades/migrate_to_v3/).

### Inferences
- Integrations built on v2.4 (SIEM webhooks, SOAR playbooks, the Python client) all break on v3; this is a window where customers re-evaluate tooling.

### Gaps
- The exact method list of the Python client was not retrievable from the index page.
- Whether v3 GA will restore bulk CSV and task-log endpoints is stated only as "open an issue so it can be prioritised".
